### 2.2 潜在问题与建议

#### 问题 2.2.1: 缺少速率限制定义

**问题描述**: 预约接口 (`POST /api/bookings`) 未定义速率限制规则。

**风险**: 恶意用户可能批量占用名额或进行 DDoS 攻击。

**建议**:
```
建议添加以下速率限制:
- 预约接口: 10次/分钟/用户
- 登录接口: 5次/分钟/IP
- 注册接口: 3次/小时/IP
```

#### 问题 2.2.2: 缺少 API 版本控制说明

**问题描述**: 未定义 API 版本控制策略。

**风险**: 后续 API 升级可能破坏客户端兼容性。

**建议**: 
- 添加 API 版本前缀 (`/api/v1/`)
- 或使用 Header 版本控制 (`Accept: application/vnd.api.v1+json`)

#### 问题 2.2.3: 批量操作接口缺失

**问题描述**: 管理后台缺少批量操作接口定义（如批量取消预约）。

**风险**: 管理效率低下。

**建议**: 补充管理后台批量操作说明，可利用 Filament 内置功能。

## 3. 数据结构审查

### 3.1 完整性评估

| 检查项 | 状态 | 说明 |
|-------|------|------|
| 主键定义 | ✅ 完整 | 所有表使用自增主键 |
| 外键约束 | ✅ 完整 | 关联关系明确 |

| 查询索引 | ✅ 完整 | 主要查询场景有索引覆盖 |
| 软删除 | ⚠️ 部分 | 仅 activities 表有软删除 |
| 审计字段 | ⚠️ 部分 | 缺少 updated_by 字段 |

### 3.2 潜在问题与建议

#### 问题 3.2.1: bookings 表缺少软删除

**问题描述**: `bookings` 表没有 `deleted_at` 字段。

**风险**: 取消的预约记录无法区分是逻辑删除还是物理删除。

**建议**: 
- 当前设计使用 `status=cancelled` 表示取消，逻辑合理
- 若需要审计追溯，可添加软删除支持

#### 问题 3.2.2: 缺少审计字段

**问题描述**: `activities` 表缺少 `updated_by` 字段。

**风险**: 无法追踪谁修改了活动信息。

**建议**:
```sql
ALTER TABLE activities ADD COLUMN updated_by BIGINT UNSIGNED NULL;
```

#### 问题 3.2.3: gallery 字段 JSON 结构未定义

**问题描述**: `activities.gallery` 字段使用 JSON 类型，但未定义具体结构。

**建议**: 补充 JSON 结构定义
```json
{
  "images": [
    {
      "url": "string",
      "alt": "string",
      "order": "integer"
    }
  ]
}
```

#### 问题 3.2.4: SQLite 生产环境风险

**问题描述**: 当前项目使用 SQLite，文档已识别但需强调。

**风险**: 
- SQLite 不支持并发写入锁
- 不适合 Web 应用生产环境
- 悲观锁策略可能失效

**建议**: 
- **必须**在开发阶段迁移至 MySQL 8.0+
- 更新 `.env` 配置和 `config/database.php`

### 4.2 潜在问题与建议

#### 问题 4.2.1: 预约状态机未明确定义

**问题描述**: 预约状态 (confirmed/cancelled/completed) 之间的转换规则未图示化。

**建议**: 补充状态机图
```
[confirmed] ──(用户取消)──► [cancelled]
[confirmed] ──(活动结束)──► [completed]
[cancelled] ──(不可逆)
[completed] ──(不可逆)
```

#### 问题 4.2.2: 活动状态与预约关系未定义

**问题描述**: 活动状态为 `cancelled` 时，已有预约如何处理未说明。

**建议**: 补充以下规则
- 活动取消时，所有 `confirmed` 预约自动变为 `cancelled`
- 发送通知给受影响用户（若有邮件功能）

#### 问题 4.2.3: 超时未完成预约处理

**问题描述**: 若预约流程中断（如用户关闭页面），是否有超时清理机制？

**分析**: 当前设计为即时创建预约，无预占机制，此问题不存在。

**状态**: ✅ 无需处理
