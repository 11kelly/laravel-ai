## 1. 背景与目标 (Background & Goals)

### 1.1 业务与技术痛点

当前业务场景需要构建一套活动预约管理系统，以支持：
- 用户在线浏览活动信息并进行预约操作
- 用户自主管理个人预约记录与资料
- 管理员通过后台系统发布活动并管理预约数据

技术层面存在以下挑战：
- 需要同时支持前台用户端与后台管理端，两套界面存在权限与数据展示差异
- 活动图片上传与存储需要平衡性能、安全性与成本
- 预约操作存在并发竞争风险，需保证数据一致性
- 用户注册登录流程需要符合安全合规要求

### 1.2 本需求明确解决的问题

本系统将解决：
1. **前台功能**：提供活动浏览、预约、用户注册登录能力
2. **个人中心**：提供预约管理、个人资料维护功能
3. **后台管理**：提供活动发布、预约审核与管理、图片上传功能
4. **技术架构**：基于 Laravel 12.0 + Filament 4.0 构建统一的技术栈

### 1.3 架构目标

#### 可扩展性 (Scalability)
- 支持活动数量与用户规模的增长，数据库查询需考虑索引优化
- 图片存储支持本地存储与云存储（S3）切换，不绑定单一存储方案
- 预约流程支持未来扩展（如支付、通知、积分等）

#### 可维护性 (Maintainability)
- 前后台功能模块化，职责边界清晰
- 使用 Filament 4.0 标准组件，降低定制化维护成本
- 数据库迁移与版本控制规范化

#### 可审计性 (Auditability)
- 关键操作（预约创建/取消、活动发布/下架）需记录操作日志
- 用户行为可追溯，支持合规审计需求

#### 非功能性需求 (NFR)
- **性能**：活动列表页首屏加载时间 < 2s（假设 1000 条活动记录）
- **可用性**：系统可用性目标 99.5%（排除计划内维护）
- **安全性**：用户密码采用 Laravel 标准哈希算法，敏感操作需认证授权

### 1.4 Out of Scope（本期不解决但已识别的问题）

以下功能不在本期范围，但已识别为未来演进方向：
- 活动支付与退款流程
- 短信/邮件通知系统集成
- 活动评价与反馈功能
- 移动端 APP 或 PWA 支持
- 多语言国际化（i18n）
- 活动分类与标签系统
- 用户积分与会员等级体系
- 第三方登录（OAuth）集成（待确认）

## 2. 核心接口定义 (API / Service Contracts)

### 2.1 前台用户接口

#### 2.1.1 活动列表查询接口

**接口职责**: 提供分页活动列表，支持筛选（状态、日期范围）

**输入参数**:
- `page` (integer, 可选): 页码，默认 1
- `per_page` (integer, 可选): 每页数量，默认 15，最大 50
- `status` (string, 可选): 活动状态筛选（`upcoming`, `ongoing`, `ended`）
- `start_date` (date, 可选): 开始日期筛选（ISO 8601）
- `end_date` (date, 可选): 结束日期筛选（ISO 8601）

**输出结构**:
- **成功响应** (HTTP 200):
  ```json
  {
    "data": [
      {
        "id": "integer",
        "title": "string",
        "description": "string",
        "image_url": "string|null",
        "start_time": "datetime",
        "end_time": "datetime",
        "capacity": "integer",
        "booked_count": "integer",
        "status": "string",
        "created_at": "datetime"
      }
    ],
    "meta": {
      "current_page": "integer",
      "per_page": "integer",
      "total": "integer",
      "last_page": "integer"
    }
  }
  ```
- **可预期失败** (HTTP 400): 参数校验失败，返回错误详情
- **不可恢复错误** (HTTP 500): 服务器内部错误，记录日志

**调用方**: 前台 Blade 视图或前端 JavaScript  
**被调用方**: Laravel Controller / Service Layer  
**幂等性**: 查询操作天然幂等  
**失败时责任归属**: 后端负责错误处理与日志记录

#### 2.1.2 活动详情查询接口

**接口职责**: 返回单个活动的完整信息

**输入参数**:
- `id` (integer, 必填): 活动 ID

**输出结构**:
- **成功响应** (HTTP 200): 活动完整对象（包含详细描述、图片、剩余名额等）
- **可预期失败** (HTTP 404): 活动不存在或已删除
- **不可恢复错误** (HTTP 500): 服务器错误

**幂等性**: 查询操作天然幂等  
**副作用**: 无

#### 2.1.3 活动预约创建接口

**接口职责**: 用户创建活动预约

**输入参数**:
- `event_id` (integer, 必填): 活动 ID
- `user_id` (integer, 必填): 用户 ID（从认证上下文获取）
- `notes` (string, 可选): 预约备注，最大长度 500

**输出结构**:
- **成功响应** (HTTP 201):
  ```json
  {
    "id": "integer",
    "event_id": "integer",
    "user_id": "integer",
    "status": "string",
    "created_at": "datetime"
  }
  ```
- **可预期失败**:
  - HTTP 400: 活动已满、活动已结束、用户已预约
  - HTTP 401: 未认证
  - HTTP 403: 权限不足
- **不可恢复错误** (HTTP 500): 数据库错误或并发冲突

**调用方**: 前台表单提交  
**被调用方**: Laravel Controller / Service Layer / Database  
**幂等性**: 非幂等操作，需通过业务规则防止重复预约（见 6.1）  
**失败时责任归属**: 后端负责事务回滚与错误提示

#### 2.1.4 用户注册接口

**接口职责**: 新用户注册

**输入参数**:
- `name` (string, 必填): 用户名，长度 2-50
- `email` (string, 必填): 邮箱，需符合邮箱格式，唯一性校验
- `password` (string, 必填): 密码，最小长度 8，需包含字母与数字（待确认）
- `password_confirmation` (string, 必填): 密码确认

**输出结构**:
- **成功响应** (HTTP 201): 用户对象（不含密码字段）
- **可预期失败**:
  - HTTP 422: 验证失败（邮箱已存在、密码不符合规则等）
- **不可恢复错误** (HTTP 500): 数据库错误

**幂等性**: 非幂等，但邮箱唯一性约束保证不会重复创建  
**副作用**: 创建用户记录，可能触发邮件验证（待确认）

#### 2.1.5 用户登录接口

**接口职责**: 用户身份认证

**输入参数**:
- `email` (string, 必填): 邮箱
- `password` (string, 必填): 密码
- `remember` (boolean, 可选): 记住登录状态

**输出结构**:
- **成功响应** (HTTP 200): 认证成功，设置 Session Cookie
- **可预期失败**:
  - HTTP 401: 邮箱或密码错误
  - HTTP 422: 参数验证失败
- **不可恢复错误** (HTTP 500): 认证服务异常

**幂等性**: 非幂等，每次登录生成新的 Session  
**副作用**: 更新用户最后登录时间，记录登录日志（待确认）

### 2.2 个人中心接口

#### 2.2.1 用户预约列表查询接口

**接口职责**: 查询当前用户的预约记录

**输入参数**:
- `user_id` (integer, 必填): 从认证上下文获取
- `status` (string, 可选): 预约状态筛选（`pending`, `confirmed`, `cancelled`）
- `page` (integer, 可选): 分页参数

**输出结构**:
- **成功响应** (HTTP 200): 预约列表（包含关联活动信息）
- **可预期失败** (HTTP 401): 未认证
- **不可恢复错误** (HTTP 500): 查询错误

**幂等性**: 查询操作天然幂等  
**授权边界**: 仅能查询当前用户自己的预约记录

#### 2.2.2 预约取消接口

**接口职责**: 用户取消已创建的预约

**输入参数**:
- `booking_id` (integer, 必填): 预约 ID
- `user_id` (integer, 必填): 从认证上下文获取

**输出结构**:
- **成功响应** (HTTP 200): 更新后的预约对象
- **可预期失败**:
  - HTTP 400: 预约不存在、不属于当前用户、已取消、活动已开始
  - HTTP 401: 未认证
- **不可恢复错误** (HTTP 500): 数据库错误

**幂等性**: 非幂等，但需处理重复取消请求（见 6.1）  
**副作用**: 更新预约状态，释放活动名额

#### 2.2.3 个人资料更新接口

**接口职责**: 更新用户个人信息

**输入参数**:
- `name` (string, 可选): 用户名
- `email` (string, 可选): 邮箱（需唯一性校验）
- `phone` (string, 可选): 手机号（待确认字段）
- `avatar` (file, 可选): 头像文件（待确认）

**输出结构**:
- **成功响应** (HTTP 200): 更新后的用户对象
- **可预期失败**:
  - HTTP 422: 验证失败（邮箱已存在等）
  - HTTP 401: 未认证
- **不可恢复错误** (HTTP 500): 更新失败

**幂等性**: 部分幂等（相同输入多次提交结果一致）  
**副作用**: 更新用户记录，可能触发邮件验证（如邮箱变更）

## 3. 数据库 / 数据结构设计 (Schema Design)

### 3.1 核心数据表

#### 3.1.1 `users` 表

**表说明**: 用户基础信息表（继承 Laravel 默认 users 表结构）

**字段定义**:
- `id` (bigint, primary key, auto increment): 用户 ID
- `name` (string, 255, not null): 用户名
- `email` (string, 255, unique, not null): 邮箱
- `email_verified_at` (timestamp, nullable): 邮箱验证时间
- `password` (string, 255, not null): 密码哈希值
- `remember_token` (string, 100, nullable): 记住登录 Token
- `created_at` (timestamp, nullable): 创建时间
- `updated_at` (timestamp, nullable): 更新时间

**索引**:
- Primary Key: `id`
- Unique Index: `email`
- Index: `email_verified_at`（用于查询已验证用户）

**并发与一致性假设**:
- 邮箱唯一性通过数据库唯一索引保证，应用层需处理唯一性冲突异常
- 密码更新需使用事务保证原子性

**数据增长预期**:
- 假设初始用户规模 1000，年增长 20%，5 年后约 2488 用户
- 查询模式：按邮箱查询（登录）、按 ID 查询（关联查询）

**向后兼容性**:
- 遵循 Laravel 默认 users 表结构，未来扩展字段需通过迁移添加

#### 3.1.2 `events` 表

**表说明**: 活动信息表

**字段定义**:
- `id` (bigint, primary key, auto increment): 活动 ID
- `title` (string, 255, not null): 活动标题
- `slug` (string, 255, unique, nullable): URL 友好标识（待确认）
- `description` (text, nullable): 活动描述
- `image_path` (string, 500, nullable): 图片存储路径
- `start_time` (datetime, not null): 活动开始时间
- `end_time` (datetime, not null): 活动结束时间
- `capacity` (integer, unsigned, not null, default 0): 最大参与人数
- `status` (enum: 'draft', 'published', 'cancelled', not null, default 'draft'): 活动状态
- `created_by` (bigint, nullable): 创建者用户 ID（外键关联 users.id）
- `created_at` (timestamp, nullable): 创建时间
- `updated_at` (timestamp, nullable): 更新时间
- `deleted_at` (timestamp, nullable): 软删除时间（如启用软删除）

**索引**:
- Primary Key: `id`
- Unique Index: `slug`（如启用）
- Index: `status`
- Index: `start_time`
- Index: `end_time`
- Composite Index: `(status, start_time)`（用于查询即将开始的活动）
- Foreign Key: `created_by` -> `users.id`（ON DELETE SET NULL）

**约束**:
- `capacity` >= 0
- `end_time` > `start_time`（应用层校验，数据库层通过 Check Constraint 或 Trigger 实现，待确认）

**并发与一致性假设**:
- 活动状态更新需使用乐观锁或悲观锁防止并发修改冲突
- 活动删除采用软删除策略（待确认），保证历史预约数据关联完整性

**数据增长预期**:
- 假设初始活动数量 100，年增长 50 个，5 年后约 350 个活动
- 查询模式：
  - 前台：按状态与时间范围查询（`status = 'published' AND start_time >= NOW()`）
  - 后台：按状态、创建者查询

**向后兼容性**:
- 新增字段需通过迁移添加，默认值需考虑现有数据兼容性

#### 3.1.3 `bookings` 表

**表说明**: 用户预约记录表

**字段定义**:
- `id` (bigint, primary key, auto increment): 预约 ID
- `event_id` (bigint, not null): 活动 ID（外键关联 events.id）
- `user_id` (bigint, not null): 用户 ID（外键关联 users.id）
- `status` (enum: 'pending', 'confirmed', 'cancelled', not null, default 'pending'): 预约状态
- `notes` (text, nullable): 用户备注
- `admin_notes` (text, nullable): 管理员备注
- `cancelled_at` (timestamp, nullable): 取消时间
- `cancelled_by` (bigint, nullable): 取消操作者用户 ID（用户自己或管理员）
- `created_at` (timestamp, nullable): 创建时间
- `updated_at` (timestamp, nullable): 更新时间

**索引**:
- Primary Key: `id`
- Unique Index: `(event_id, user_id)`（防止同一用户重复预约同一活动）
- Index: `user_id`
- Index: `event_id`
- Index: `status`
- Index: `created_at`
- Composite Index: `(user_id, status)`（用于查询用户特定状态的预约）
- Foreign Key: `event_id` -> `events.id`（ON DELETE RESTRICT，防止删除有预约的活动）
- Foreign Key: `user_id` -> `users.id`（ON DELETE CASCADE，用户删除时级联删除预约）

**约束**:
- 唯一性约束：同一用户不能重复预约同一活动（通过唯一索引保证）

**并发与一致性假设**:
- **关键并发场景**：多个用户同时预约同一活动，需保证名额不超限
  - 方案：使用数据库事务 + 行级锁（SELECT FOR UPDATE）或乐观锁（版本号字段）
  - 推荐方案：事务 + 行级锁，在事务内查询当前已预约数量并校验
- 预约创建需在事务内完成，保证活动名额更新与预约记录创建的原子性

**数据增长预期**:
- 假设每个活动平均 20 个预约，初始 100 个活动约 2000 条预约记录
- 年增长约 1000 条，5 年后约 7000 条预约记录
- 查询模式：
  - 用户端：按用户 ID 与状态查询
  - 管理端：按活动 ID 查询、按状态筛选

**向后兼容性**:
- 状态枚举值扩展需谨慎，避免影响现有数据查询逻辑

### 3.2 数据迁移风险

**风险点**:
1. 唯一索引创建可能因现有重复数据失败，需先清理数据
2. 外键约束添加需确保关联数据完整性
3. 枚举值修改需通过 ALTER TABLE 操作，可能影响现有查询

**缓解措施**:
- 迁移前执行数据完整性检查脚本
- 使用 Laravel Migration 的 `down()` 方法支持回滚
- 生产环境迁移前在 Staging 环境充分测试

## 5. 核心业务流程 (Business Flow)

### 5.1 活动预约流程（正常流程）

**流程步骤**:

1. **用户浏览活动列表**
   - 用户访问 `/events`
   - 系统查询 `events` 表，筛选 `status = 'published' AND start_time >= NOW()`
   - 返回分页活动列表，展示活动标题、图片、时间、剩余名额

2. **用户查看活动详情**
   - 用户点击活动项，访问 `/events/{id}`
   - 系统查询活动详情，关联查询已预约数量
   - 展示活动完整信息，如剩余名额 > 0，显示"立即预约"按钮

3. **用户创建预约**
   - 用户点击"立即预约"按钮
   - **前置校验**：
     - 用户是否已登录（未登录跳转登录页）
     - 活动是否存在且状态为 `published`
     - 活动是否已开始（`start_time > NOW()`）
     - 活动是否已满（`booked_count >= capacity`）
     - 用户是否已预约该活动（查询 `bookings` 表唯一索引）
   - **事务开始**：
     - 锁定活动记录（`SELECT FOR UPDATE`）
     - 重新查询当前已预约数量（防止并发超限）
     - 校验名额是否充足
     - 创建预约记录（`bookings` 表 INSERT）
     - 更新活动已预约数量（如使用计数器字段，待确认）
   - **事务提交**
   - 返回成功响应，跳转至个人中心预约列表页

4. **用户查看预约记录**
   - 用户访问 `/profile/bookings`
   - 系统查询当前用户的预约记录，关联查询活动信息
   - 展示预约列表，支持按状态筛选

### 5.2 预约取消流程

**流程步骤**:

1. **用户发起取消**
   - 用户在个人中心点击"取消预约"
   - **前置校验**：
     - 预约是否存在且属于当前用户
     - 预约状态是否为 `pending` 或 `confirmed`
     - 活动是否已开始（`start_time > NOW()`）
   - **事务开始**：
     - 更新预约状态为 `cancelled`
     - 设置 `cancelled_at` 与 `cancelled_by`
     - 释放活动名额（减少已预约数量）
   - **事务提交**
   - 返回成功响应

### 5.3 活动发布流程（后台）

**流程步骤**:

1. **管理员创建活动**
   - 管理员登录 Filament Admin Panel
   - 访问活动管理页面，点击"创建活动"
   - 填写活动表单（标题、描述、时间、名额等）
   - 上传活动图片（可选）
   - 提交表单

2. **图片上传处理**
   - Filament FileUpload 组件调用图片上传接口
   - 校验文件格式、大小、尺寸
   - 生成唯一文件名（UUID 或时间戳 + 随机字符串）
   - 存储至 `storage/app/public/events/` 目录
   - 返回图片 URL

3. **活动数据保存**
   - 验证表单数据（时间逻辑、名额限制等）
   - 保存活动记录至 `events` 表
   - 关联图片路径
   - 设置 `status = 'draft'`（默认草稿状态）

4. **活动发布**
   - 管理员编辑活动，将状态改为 `published`
   - 活动在前台列表页可见

### 5.4 异常 / 中断流程

#### 5.4.1 并发预约冲突

**场景**: 多个用户同时预约同一活动，剩余名额为 1

**处理流程**:
1. 用户 A 与用户 B 同时提交预约请求
2. 两个请求进入事务，均执行 `SELECT FOR UPDATE` 锁定活动记录
3. 用户 A 的事务先获取锁，查询当前已预约数量，校验通过，创建预约，提交事务
4. 用户 B 的事务获取锁，查询当前已预约数量，发现已满，返回错误响应（HTTP 400）
5. 用户 B 收到"活动已满"提示

**责任归属**: 后端通过数据库锁机制保证一致性，前端需友好提示用户

#### 5.4.2 活动删除冲突

**场景**: 管理员删除活动时，该活动存在未取消的预约

**处理流程**:
1. 管理员尝试删除活动
2. 数据库外键约束（`ON DELETE RESTRICT`）阻止删除
3. 系统返回错误提示，要求先处理预约记录
4. 管理员可选择：
   - 取消所有预约后删除活动
   - 或采用软删除策略（设置 `deleted_at`），保留历史数据

**责任归属**: 数据库约束保证数据完整性，应用层需处理约束异常

### 5.5 关键状态变更点

**活动状态变更**:
- `draft` -> `published`: 活动发布，前台可见
- `published` -> `cancelled`: 活动取消，前台不可预约，已预约用户需通知（待确认）

**预约状态变更**:
- `pending` -> `confirmed`: 管理员确认预约（待确认是否需要此状态）
- `pending/confirmed` -> `cancelled`: 用户或管理员取消预约

## 6. 边缘情况与一致性问题 (Edge Cases & Consistency)

### 6.1 并发 / 重复请求

#### 6.1.1 重复预约防护

**问题**: 用户快速点击"立即预约"按钮，可能产生重复请求

**解决方案**:
1. **前端防抖（Debounce）**: 按钮点击后禁用 2 秒，防止重复提交
2. **后端唯一索引**: 数据库唯一索引 `(event_id, user_id)` 保证同一用户不能重复预约同一活动
3. **幂等性处理**: 如检测到重复预约（唯一索引冲突），返回友好错误提示而非系统错误

**责任归属**: 前端负责用户体验优化，后端负责数据一致性保证

#### 6.1.2 活动名额并发更新

**问题**: 多个用户同时预约，需保证名额计数准确性

**解决方案**:
- 使用数据库事务 + 行级锁（`SELECT FOR UPDATE`）
- 在事务内重新查询当前已预约数量，避免使用缓存计数器
- 如使用计数器字段，需使用原子操作（`UPDATE events SET booked_count = booked_count + 1 WHERE id = ?`）

**一致性保证**: 数据库 ACID 特性保证事务内操作原子性

### 6.2 数据竞争或唯一性冲突

#### 6.2.1 邮箱唯一性冲突

**场景**: 用户注册时邮箱已存在

**处理**: 
- 数据库唯一索引保证唯一性
- 应用层捕获唯一性约束异常，返回 HTTP 422 错误，提示"邮箱已被注册"

#### 6.2.2 活动 Slug 唯一性冲突（如启用）

**场景**: 自动生成的活动 Slug 可能重复

**处理**:
- 使用 UUID 或时间戳 + 随机字符串生成唯一 Slug
- 如检测到重复，追加随机后缀重试

### 6.3 异常中断后的恢复假设

#### 6.3.1 预约创建事务中断

**场景**: 事务执行过程中数据库连接中断

**处理**:
- 数据库事务自动回滚，保证数据一致性
- 用户需重新提交预约请求
- 系统记录错误日志，便于排查问题

#### 6.3.2 图片上传中断

**场景**: 图片上传过程中网络中断

**处理**:
- 未完成的上传文件不会保存至存储目录
- 用户需重新上传图片
- 考虑实现断点续传功能（待确认，非本期范围）

  **When** 用户点击"立即预约"按钮

- **Given** 用户未登录  
  **When** 用户点击"立即预约"按钮  
  **Then** 跳转至登录页，登录后返回原活动详情页

- **Given** 活动已满  
  **When** 用户尝试预约  
  **Then** 显示"活动已满"错误提示，不创建预约记录

- **Given** 用户已预约某活动  
  **When** 用户再次尝试预约同一活动  
  **Then** 显示"您已预约该活动"错误提示，不创建重复预约

#### 10.1.2 个人中心功能验收

- **Given** 用户已登录  
  **When** 用户访问个人中心预约列表  
  **Then** 显示当前用户的所有预约记录，包含活动信息、预约状态、创建时间

- **Given** 用户有未取消的预约  
  **When** 用户点击"取消预约"按钮  
  **Then** 预约状态更新为 `cancelled`，活动剩余名额加 1

- **Given** 活动已开始  
  **When** 用户尝试取消预约  
  **Then** 显示"活动已开始，无法取消"错误提示

#### 10.1.3 后台管理功能验收

- **Given** 管理员已登录  
  **When** 管理员创建活动并上传图片  
  **Then** 活动记录保存成功，图片存储至指定目录，返回图片 URL

- **Given** 管理员发布活动  
  **When** 活动状态改为 `published`  
  **Then** 活动在前台列表页可见

- **Given** 活动存在未取消的预约  
  **When** 管理员尝试删除活动  
  **Then** 显示错误提示，要求先处理预约记录

### 10.2 数据一致性

#### 10.2.1 预约名额一致性

- **Given** 活动剩余名额为 1  
  **When** 两个用户同时提交预约请求  
  **Then** 仅一个用户预约成功，另一个用户收到"活动已满"提示，活动名额为 0

#### 10.2.2 预约记录完整性

- **Given** 用户创建预约  
  **When** 查询预约记录  
  **Then** 预约记录包含正确的 `event_id`、`user_id`、`status`、`created_at`

### 10.3 性能 / 安全底线

#### 10.3.1 性能验收

- 活动列表页首屏加载时间 < 2s（1000 条活动记录，分页 15 条/页）
- 预约创建 API 响应时间 < 500ms（不含网络传输）
- 图片上传（5MB）处理时间 < 3s

#### 10.3.2 安全验收

- 用户密码使用 bcrypt 加密存储，不在数据库中以明文形式存在
- 未登录用户无法访问个人中心页面（返回 401 或跳转登录页）
- 非管理员用户无法访问后台管理页面（返回 403）
- 用户仅能查看和操作自己的预约记录

### 10.4 可测试性声明

- 所有 Service Layer 业务逻辑可通过单元测试验证
- 预约创建流程可通过集成测试验证
- 并发预约场景可通过压力测试验证（待确认）

## 11. 风险、限制与技术决策 (Risks & Trade-offs)

### 11.1 已识别风险

#### 11.1.1 技术风险

**风险 1: 并发预约导致名额超限**

- **影响**: 高（影响核心功能正确性）
- **概率**: 中（高并发场景下可能出现）
- **缓解措施**: 
  - 使用数据库事务 + 行级锁保证一致性
  - 压力测试验证并发场景
- **状态**: 已识别，需在开发阶段验证

**风险 2: 图片存储空间不足**

- **影响**: 中（影响活动发布功能）
- **概率**: 低（初期数据量较小）
- **缓解措施**: 
  - 定期清理未使用的图片文件
  - 生产环境迁移至云存储（S3），支持自动扩容
- **状态**: 已识别，需制定存储管理策略

**风险 3: Filament 4.0 版本兼容性**

- **影响**: 中（影响后台管理功能）
- **概率**: 低（使用官方稳定版本）
- **缓解措施**: 
  - 遵循 Filament 官方文档与最佳实践
  - 避免修改核心代码，使用扩展点
- **状态**: 已识别，需关注 Filament 版本更新

#### 11.1.2 业务风险

**风险 4: 用户恶意刷单**

- **影响**: 中（影响活动公平性）
- **概率**: 低（初期用户规模较小）
- **缓解措施**: 
  - 记录用户预约行为日志，支持后续分析
  - 未来可实施预约限制策略（如：同一用户单日预约上限）
- **状态**: 已识别，非本期范围，需未来演进

**风险 5: 活动删除导致历史数据丢失**

- **影响**: 低（影响数据完整性）
- **概率**: 低（管理员操作）
- **缓解措施**: 
  - 采用软删除策略，保留历史数据
  - 数据库外键约束防止误删
- **状态**: 已识别，需确认删除策略

### 11.2 架构取舍及原因

#### 11.2.1 使用 Filament 4.0 而非自定义后台

**取舍**: 使用 Filament 标准组件，减少定制化开发

**原因**:
- 降低开发与维护成本
- 利用 Filament 成熟的安全与权限机制
- 快速迭代，符合项目时间要求

**代价**:
- 定制化能力受限，需遵循 Filament 设计模式
- 学习成本（团队需熟悉 Filament）

#### 11.2.2 使用数据库行级锁而非乐观锁

**取舍**: 使用悲观锁（`SELECT FOR UPDATE`）保证并发预约一致性

**原因**:
- 预约场景下冲突概率较高，悲观锁更直接有效
- 数据库锁机制成熟可靠，减少应用层复杂度

**代价**:
- 可能造成请求排队，影响响应时间
- 需合理设计锁粒度，避免死锁

#### 11.2.3 图片存储使用本地存储（开发）与云存储（生产）

**取舍**: 开发环境使用本地存储，生产环境使用 S3

**原因**:
- 开发环境简化配置，降低本地开发门槛
- 生产环境使用云存储，支持高可用与自动扩容

**代价**:
- 需维护两套存储配置
- 迁移时需考虑数据一致性

### 11.3 延后处理的问题与演进方向

#### 11.3.1 本期不实现的功能

1. **支付与退款**: 活动预约如需付费，需集成支付网关
2. **通知系统**: 预约成功、活动提醒等需短信/邮件通知
3. **移动端支持**: PWA 或原生 APP 支持
4. **多语言**: 国际化支持
5. **活动分类**: 活动分类与标签系统
6. **用户积分**: 会员等级与积分体系

#### 11.3.2 未来演进方向

1. **性能优化**:
   - 引入 Redis 缓存活动列表
   - 数据库读写分离
   - CDN 加速图片访问

2. **功能扩展**:
   - 活动评价与反馈
   - 活动推荐算法
   - 用户社交功能（待确认）

3. **安全增强**:
   - 双因素认证（2FA）
   - 异常登录检测与告警
   - API 限流与防刷机制

4. **数据分析**:
   - 活动参与度分析
   - 用户行为分析
   - 数据报表与可视化
